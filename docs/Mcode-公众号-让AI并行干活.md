# 让 4 个 AI 同时给我干活一周,我发现瓶颈根本不是模型

周一早上九点,我给自己派了四个活:重构一个老模块、修一个拖了三天的 bug、给核心代码补测试、写一份技术文档。四个 AI 会话,同时开跑。

听起来很美好,对吧?

十分钟后,我的工作变成了这样:点开会话一,还在跑;切到会话二,在等我审批;切到会话三,跑完了一段,得看看它改了什么;切到会话四——刚才它改的是哪个文件来着?

**我不是在指挥四个 agent,我是在给它们当人肉轮询器。**

这个状态持续了一周。某天晚上我复盘,发现自己每天的操作里大约四成是"切换会话窗口"——剩下的时间,才轮到真正的工作:看代码、做决策、按确认。模型很快,我的注意力跟不上。

那一刻我想明白了一件事:**单会话时代的 AI 编程问题——上下文管理、diff 查看、工具审批——各家工具已经解决得七七八八;但并行时代的问题,几乎没人管。**模型可以同时开四条线干活,你的屏幕、你的 git、你的注意力,还是单线程的。

后来我把这些思考做进了我维护的开源项目 Mcode(一个桌面端 AI 编程 IDE,基于 Claude Agent SDK,同时接了多家 agent)。这篇文章不聊参数和架构,只聊四条我亲身踩出来的教训,以及每条教训背后,工具该怎么改。

---

## 教训一:切换成本,比模型延迟贵

先算一笔账。每次切换会话,你要重建一次上下文:这个会话在干嘛?跑到哪了?上一条输出是啥?哪怕每次只花五秒,四个会话轮一圈就是二十秒——而且这个轮询是没有尽头的,任务不停,轮询不停。

真正贵的不是这二十秒,是**你的工作状态被打断了**。你本来在深读会话三改的那段代码,切去看会话一的进度,再回来时,刚才读到的第七行是什么来着?

解法其实很朴素:**让它们同屏。**

我现在的工作面是这样的:四个会话排成一屏四格(两个就左右分,三个就上二下一),像监控墙一样。哪个格子出结果,视线挪过去就行——注意力不用搬家。底部一条共享输入框,光标聚焦在哪个格子,消息就发给哪个会话,想给谁派活就点谁。

两个容易做错的地方,也说一下:

- **配置不能串。**四个格子可能跑着四个不同的模型、不同的权限档。如果 A 格子的排队消息用了 B 格子的配置,你以为是便宜的模型在跑,账单给你惊喜。每个格子必须严格按自己的配置发送。
- **终端也是会话。**有些活我直接开终端里的 claude/opencode 干,它们同样能拖进格子,四个格子混着 GUI 会话和终端会话,一视同仁。

拖进去就行:从左侧会话列表把会话拖到中间区域,松手入格。就这么个动作,我从"人肉轮询器"变回了"盯着监控墙的指挥官"。

## 教训二:看一眼,不该以打断为代价

同屏解决了"盯任务",但很快我发现第二个问题:屏幕就那么大,侧栏一推开,布局跟着跳,正在看的代码直接被挤走。

最典型的时刻:会话输出里提到一个文件,我想确认一眼它的位置或内容——点开侧栏,文件树展开,聊天流被挤得滚动条一跳,回来还得重新找刚才读到哪。

需求的本质是"**瞄一眼**",而不是"打开并停留"。瞄一眼的代价,不应该是一次布局地震。

现在的交互是:侧栏关着的时候,鼠标贴到屏幕边缘停一下(零点一几秒),面板像抽屉一样浮出来,浮在内容**之上**——不挤压任何东西;鼠标移开,它自己滑回去。左边贴边是会话列表,右边贴边是文件树和 git。

有个细节我很喜欢:右栏关着时,如果我在聊天里点开一个文件,文件树会自己滑出来展示它,几秒没人理会就默默收回去。它像个有分寸的助手,而不是需要你随手关门的柜子。

多显示器的朋友应该懂另一个痛点:光标从旁边屏幕横着移过来,经常直接越过窗口边缘的那条感应区,落不到点上。所以屏幕边缘之外,标题栏上也埋了一个热区接住这种"从天而降"的光标——这是被自己坑了之后才补的。

## 教训三:AI 干得越快,你的 git 越像事故现场

并行还有一个副作用,当时完全没预料到:**改动堆积的速度快过了我提交的速度。**

四个 agent 同时产出,一个下午下来,变更列表里躺着一百多个文件,分属四条完全不相干的任务线。"等忙完这波一起提交"的后果是:真到提交时,我已经分不清哪块改动属于哪个会话,只能靠 git diff 考古。而任何一个 agent 此时手一抖改错东西,我都没有回滚点。

结论:**AI 时代,提交的摩擦力必须趋近于零。**改动不隔夜,是一条纪律。

以前提交的链路是:切到 git 面板 → 找到仓库 → stage → 憋 commit message → 提交。别小看这条链,摩擦力够大的时候,人就是会"等会儿再说"。

现在它变成了标题栏上的一个数字:分支名旁边常驻变更计数,改了几个文件一眼可见。点开,AI 已经基于这次的 diff 起草好了 commit message,我觉得行,点"提交并推送",三秒钟,这波改动落袋为安。

大改动当然还是要进 git 面板逐文件审。但高频小提交这个场景,摩擦力必须干掉——否则纪律敌不过惰性。

## 教训四:别把所有任务押在同一家 agent 上

前面三条教训都是"怎么管理并行的 agent",第四条回到一个更上游的问题:**这些 agent,非得是同一家吗?**

用下来各家确实各有擅长:有的写测试细,有的重构激进,有的便宜适合跑批量杂活。把重构交给擅长重构的、把文档丢给便宜的,分而治之,这才是并行时代的正确打开方式。而且不同家的 agent 同时跑在同一个项目里,还有个隐性好处——互相 review 对方的改动时,反而更客观(笑)。

所以 Mcode 接入了第四家 agent 后端 OpenCode:既可以作为 GUI 会话跑(审批卡、用量统计、子代理,全套管理能力照常),也可以作为终端会话跑你自己的 opencode CLI——和你终端里那个共享登录态,免费模型甚至不登录就能直接用。

四个格子,四个 agent,各干各的,一屏收阅。

---

## 最后想说的事

这一轮更新做完,我回头看,四个功能其实在回答同一个问题:

**当 AI 把"写代码"的成本降到接近零,开发者的工作变成了派活、监督、验收。那么工具该进化成驾驶舱,而不是一个更大的聊天窗口。**

模型在卷智能,终端在卷原生体验,而"人怎么同时指挥多个 AI"这件事,才刚刚开始被认真对待。现在所有工具都默认你一次只跑一个会话——这个假设,正在过时。

Mcode 是我用业余时间维护的开源项目(MIT),上面的四条教训都已经在最新版里落地。如果你也在让 AI 并行干活,试试把会话拖进格子里的感觉——回不去的。

GitHub 搜 Mcode,或者应用内直接更新。
