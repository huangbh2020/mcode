红框标出的两条标签,左边是会话(标题恰好长得像文件名)、右边是文件 —— 形态、圆角、字号、静止/激活配色完全一致,只有前置图标和等宽字体这点差别。

为什么容易搞混

  • 形态完全同构:两者都是 rounded-md px-2.5 py-1 text-[11px],静止态 bg-surface-muted/60、激活态 bg-accent/15 + ring-accent/40 逐字相同(见 SessionTabs.tsx 与 OpenTabsBar.tsx 的 SortableFileTab)。唯一差异是前置图标与文件名等宽字体。
  • 后果不对称:点会话 → 整个中栏换成对话;点文件 → 整个中栏换成编辑器。同构的 chip 承载了「模式切换」这种重后果。
  • 作用域不同却并列:会话列表是全局的(openTabs),文件列表是当前项目的(ideOpenFilesByProject[pid])。切到别的项目的会话时,右侧整组标签会静默换掉 —— 让人觉得「我的标签去哪了」。
  • 焦点丢失:isActive={id === activeId && !editorFocused} —— 编辑器聚焦时,当前会话标签没有任何标记。这条正是「我到底在哪」的困惑来源。
  • 关闭语义不同、却同一颗 ×:会话 × 只关标签、不中断运行中的回合;文件脏了根本没有 ×。两种语义共用一个图标。
  • 分组线会消失:1px 发丝线只在两组都有内容时渲染;只剩一组时它与普通单组标签条无法区分。
现状标签形态还有一处「反向线索」:会话标题可以是任意自然语言(甚至刚好写成文件名,如本例),而文件名永远像文件名 —— 靠图标区分的方向本身就不可靠。

做法

  • 上层 = 会话条(常驻,全局):回答「我在哪条对话 / 还能切去哪」。永远不被文件挤走,所以会话切换、运行中转圈、未读徽章都在一条稳定的横线上。
  • 下层 = 编辑器条(仅在编辑器聚焦时出现,bg 略深一档、更薄):回答「这个编辑器里开着哪些文件」。它带自己的身份前缀 编辑区 · cc-gui,顺手把「文件列表是项目作用域」这件事说清楚。
  • 会话锚点态:编辑器聚焦时,你所在的那条会话用「左侧 2px 强调条 + 微弱底色」标记(不是填充),和「激活填充 = 当前视图」明确区分。回对话的目标一眼可见。
  • 对话态把编辑器条整条收起,只在会话条右端留一个 已打开 4 个文件 › 的锚点 chip —— 既不浪费那 30px,也不会「文件凭空消失」。
对照:VS Code 的编辑器组 tab 就挂在编辑器面板自己的头上,而不是和窗口级导航混在一条栏里。会话条在此扮演「窗口级导航」。

取舍

  • + 结构上不可能误点:两条栏各只装一种标签,类型混淆这一整类问题消失。
  • + 会话条变稳定,不再随编辑器开合改变内容,会话前后切换的肌肉记忆成立。
  • + 顺手获得「编辑器条自带项目名」「会话锚点态」两个修正点;会话条还能加 + 新建会话,补上现在 tab 模式缺少的新建入口。
  • − 编辑器聚焦时多一行(~30px)。因为编辑器条在编辑器面板内部、随面板一起出现,切会话时它是整块隐藏/显示的,不会造成内容上下跳动。
  • − 实现量最大:两条独立 strip 的溢出/多行/拖拽状态各一套(可共用现有 TabBarChrome 与 ScrollStrip 逻辑)。

做法

  • 会话 = 药丸(pill):rounded-full + 前置项目色字母头像(和左栏会话卡的头像同一个色块,强化「这是一条对话」),状态圆点/未读徽章收在尾部。
  • 文件 = 方片(chip):保持 rounded-md + 文件类型图标 + 等宽文件名,并整体放进一个浅色底板容器里,让「编辑区」成为一个有边界的物件,而不是和会话同流。
  • 组标题代替发丝线:会话 3 / 编辑区 cc-gui 4。数量让用户知道「还有几个」;项目名把文件组是项目作用域这件事摆在明面上 —— 切项目时整组换掉就不再意外。发丝线换成 ~30px 的实际留白,不再会「只剩一组就消失」。
  • 两个状态分开表达:激活填充=当前视图;锚点态(药丸描边 + 标题加粗 + 无填充)=当前会话。编辑器聚焦时,会话药丸显示锚点态,于是「我从哪来、要回哪去」始终可见。
  • 会话组尾部补 + 新建会话,与方案 A 一致,顺手补上 tab 模式缺的新建入口。
形态先例:Slack 用 #频道 vs @头像 区分两类会话;Linear 用「视图 / 议题」两种容器形态。形状差异(圆 vs 方)在余光里就能分辨,不需要看清图标。

取舍

  • + 零布局改动:还是一条 strip、同样的滚动/多行/拖拽骨架,改动集中在 chip 样式 + 两个标题 + 一处高亮语义。
  • + 不增加高度,不引入第二条滚动条,不打断任何现有交互(溢出菜单、多行换行、中键关闭、右键菜单、跨类拖拽忽略都原样可用)。
  • + 组标题 + 项目名顺手修掉「作用域不一致」与「分组线消失」两个坑。
  • − 仍然是一条 strip:误点风险降低但不为零(组标题占了两个位置,窄窗口下它们是最先被挤掉的内容 —— 需要保留「挤不下时标题收成图标」的降级)。
  • − 药丸比方片略宽(全圆角 + 头像),同样窗口宽度下能显示的会话数略少。

做法

  • 会话降级为「头像轨道」:每条会话一个项目色字母块(复用左栏 projectAvatar 的调色板),当前会话展开成一颗带标题的药丸,其余只留色块 + hover 标题气泡。运行中的会话在色块右下角带一个脉冲小点。
  • 文件独占带标题的标签条:因为 strip 里只剩文件一种,标题 编辑区 · cc-gui 可以当作纯粹的区段名,不再承担「区分两类」的职责。
  • 会话与文件之间是 ~30px 留白 + 1px 分隔,不再是会消失的细线。
  • 当前会话始终展开,所以在编辑器里也不会丢失「回哪去」的锚点;切换会话 = 点色块,色块原地展开成药丸(有明确的形变动画可做)。
形态先例:Slack / Discord 的工作区切换器、Chrome 的标签组折叠。核心是「长期存在的身份」用紧凑色块表达,「当下在处理的内容」才配给标题宽度。

取舍

  • + 会话数增长时占用恒定,横向空间几乎全给文件标签;窗口窄时表现最好。
  • + 会话切换从「读标题」变成「认色块 + 字母」,熟练后更快;左栏与其色块同源,跨面板识别一致。
  • − 标题默认不可见:会话名首字母相近(或同一项目下多条会话)时,只靠色块 + 两字母很难区分,要 hover 才知道。这是本方案最实在的代价。
  • − 未读徽章、运行状态只能收成一个小点,信息密度下降。
  • − 拖拽重排的语义变弱(色块拖拽不如标签直观),可能干脆放弃会话重排,只保留文件重排。

做法与取舍

  • strip 永远只装当前视图的标签(对话→会话标签,编辑器→文件标签),另一侧用一颗锚点 chip 表达「另一处有什么、怎么回去」。类型混淆在构造上归零。
  • 与 方案 A 的区别:不占两行,以「一次点击」为代价 —— 从对话想直接跳到某个具体文件时,得先点 编辑区 · 4 个文件 再选。
  • 这一条就是否决理由:「agent 刚提到某文件、我要点开看」是本应用的高频动作,现状一次点击可达,方案 D 变成两次。除非给锚点 chip 加「按住即展开文件列表」这类补偿交互,否则不建议。
  • 保留价值:如果将来 tab 模式进一步压缩(比如窄屏/移动壳),D 是空间最省的退化形态。

四个方案都建议一并做的修正

① 文件组标注所属项目

文件标签存在 ideOpenFilesByProject[activeProjectId],是项目作用域;会话标签是全局的。切到别的项目的会话时右侧整组会换掉,而界面上没有任何提示。在文件组前固定标注项目名(方案 B/C 的 编辑区 · cc-gui),这类「标签去哪了」的困惑直接消失。

② 编辑器聚焦时保留会话锚点

isActive={id === activeId && !editorFocused} 让当前会话在编辑器里完全没有标记。把「视图焦点」和「会话锚点」拆成两种视觉:填充 = 正在看它,描边/侧边条 = 我是从这里来的。

③ 关闭语义的提示

会话的 × 只关标签、不中断运行中的回合;文件脏了则没有 ×。建议 hover 时给出明确说明(「关闭标签,会话继续运行」/「未保存,请先保存」),让「× 点了会怎样」可预期。

④ 溢出菜单也按组分节

TabBarOverflowMenu 现在把两类标签平铺成一条列表,同样混淆。加两个小节标题(会话 / 编辑区 · 项目),与条上的分组口径保持一致。

⑤ 多行模式下的分组也要成立

多行换行时两类标签会混在同一片网格里,分组线彻底失效。无论选哪个方案,都要保证换行后「会话块」与「文件块」仍是两片,而不是交错。

⑥ 新建会话入口

tab 模式目前没有新建会话的按钮(要去左栏)。在会话组尾部补一个 +,与「会话组」这个语义块绑定,顺带强化分组的存在感。
