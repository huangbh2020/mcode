中栏 Tab 条重设计 · 会话 vs 文件 · 含窄宽度

tabs 显示模式下,会话标签与文件标签混在同一条 strip 里(vscode 式)。现状两者用完全相同的 chip 样式, 只靠「品牌图标 vs 文件图标」和一条 1px 发丝线区分 —— 点击后果却完全不同:一个切对话、一个切编辑器。 下面给出四个方向的取舍,以及五个宽度档位上的降级规则(Tier XL → XS)。

红框标出的两条标签,左边是会话(标题恰好长得像文件名)、右边是文件 —— 形态、圆角、字号、静止/激活配色完全一致,只有前置图标和等宽字体这点差别。

为什么容易搞混

  • 形态完全同构:两者都是 rounded-md px-2.5 py-1 text-[11px],静止态 bg-surface-muted/60、激活态 bg-accent/15 + ring-accent/40 逐字相同(见 SessionTabs.tsx 与 OpenTabsBar.tsx 的 SortableFileTab)。唯一差异是前置图标与文件名等宽字体。
  • 后果不对称:点会话 → 整个中栏换成对话;点文件 → 整个中栏换成编辑器。同构的 chip 承载了「模式切换」这种重后果。
  • 作用域不同却并列:会话列表是全局的(openTabs),文件列表是当前项目的(ideOpenFilesByProject[pid])。切到别的项目的会话时,右侧整组标签会静默换掉 —— 让人觉得「我的标签去哪了」。
  • 焦点丢失:isActive={id === activeId && !editorFocused} —— 编辑器聚焦时,当前会话标签没有任何标记。这条正是「我到底在哪」的困惑来源。
  • 关闭语义不同、却同一颗 ×:会话 × 只关标签、不中断运行中的回合;文件脏了根本没有 ×。两种语义共用一个图标。
  • 分组线会消失:1px 发丝线只在两组都有内容时渲染;只剩一组时它与普通单组标签条无法区分。
  • 窄屏下图标这条线索还会失效:宽度不够时前置图标被挤掉的最先就是它 —— 详见窄宽度阶梯。
现状标签形态还有一处「反向线索」:会话标题可以是任意自然语言(甚至刚好写成文件名,如本例),而文件名永远像文件名 —— 靠图标区分的方向本身就不可靠。

做法

  • 上层 = 会话条(常驻,全局):回答「我在哪条对话 / 还能切去哪」。永远不被文件挤走,所以会话切换、运行中转圈、未读徽章都在一条稳定的横线上。
  • 下层 = 编辑器条(仅在编辑器聚焦时出现,bg 略深一档、更薄):回答「这个编辑器里开着哪些文件」。它带自己的身份前缀 编辑区 · cc-gui,顺手把「文件列表是项目作用域」这件事说清楚。
  • 会话锚点态:编辑器聚焦时,你所在的那条会话用「左侧 2px 强调条 + 微弱底色」标记(不是填充),和「激活填充 = 当前视图」明确区分。回对话的目标一眼可见。
  • 对话态把编辑器条整条收起,只在会话条右端留一个 已打开 4 个文件 › 的锚点 chip —— 既不浪费那 30px,也不会「文件凭空消失」。
对照:VS Code 的编辑器组 tab 就挂在编辑器面板自己的头上,而不是和窗口级导航混在一条栏里。会话条在此扮演「窗口级导航」。

取舍 窄屏最优

  • + 结构上不可能误点:两条栏各只装一种标签,类型混淆这一整类问题消失 —— 而且这个保证在任何宽度下都成立,不需要降级规则。
  • + 会话条变稳定,不再随编辑器开合改变内容,会话前后切换的肌肉记忆成立。
  • + 顺手获得「编辑器条自带项目名」「会话锚点态」两个修正点;会话条还能加 + 新建会话,补上现在 tab 模式缺少的新建入口。
  • − 编辑器聚焦时多一行(~30px)。因为编辑器条在编辑器面板内部、随面板一起出现,切会话时它是整块隐藏/显示的,不会造成内容上下跳动。
  • − 实现量最大:两条独立 strip 的溢出/多行/拖拽状态各一套(可共用现有 TabBarChrome 与 ScrollStrip 逻辑)。
窄屏代价几乎为零:两条栏各自独立溢出滚动,不需要「标题让位」这类降级 —— 这正是它在窄屏反而变强的理由。

做法

  • 会话 = 药丸(pill):rounded-full + 前置项目色字母头像(和左栏会话卡的头像同一个色块,强化「这是一条对话」),状态圆点/未读徽章收在尾部。
  • 文件 = 方片(chip):保持 rounded-md + 文件类型图标 + 等宽文件名,并整体放进一个浅色底板容器里,让「编辑区」成为一个有边界的物件,而不是和会话同流。
  • 组标题代替发丝线:会话 3 / 编辑区 cc-gui 4。数量让用户知道「还有几个」;项目名把文件组是项目作用域这件事摆在明面上 —— 切项目时整组换掉就不再意外。发丝线换成 ~30px 的实际留白,不再会「只剩一组就消失」。
  • 两个状态分开表达:激活填充=当前视图;锚点态(药丸描边 + 标题加粗 + 无填充)=当前会话。编辑器聚焦时,会话药丸显示锚点态,于是「我从哪来、要回哪去」始终可见。
  • 会话组尾部补 + 新建会话,与方案 A 一致,顺手补上 tab 模式缺的新建入口。
形态先例:Slack 用 #频道 vs @头像 区分两类会话;Linear 用「视图 / 议题」两种容器形态。形状差异(圆 vs 方)在余光里就能分辨,不需要看清图标。

取舍

  • + 零布局改动:还是一条 strip、同样的滚动/多行/拖拽骨架,改动集中在 chip 样式 + 两个标题 + 一处高亮语义。
  • + 不增加高度,不引入第二条滚动条,不打断任何现有交互(溢出菜单、多行换行、中键关闭、右键菜单、跨类拖拽忽略都原样可用)。
  • + 组标题 + 项目名顺手修掉「作用域不一致」与「分组线消失」两个坑。
  • − 窄屏要额外设计:组标题、头像都是「宽度换信息」的元素,窄窗口下它们是最先被挤掉的 —— 必须补一套降级阶梯(下面整节).
  • − 仍然是一条 strip:误点风险降低但不为零。
  • − 药丸比方片略宽(全圆角 + 头像),同样窗口宽度下能显示的会话数略少。

窄屏上的关键取舍 见下节

B 的三条区分线索(形状 / 组标题 / 头像)里,只有形状不占宽度。所以窄屏降级的正确顺序是: 先收组标题 → 再收头像 → 最后才动形状。反过来说,药丸/方片的形状分化必须做成基底样式而不是「宽屏增强」—— 它是窄屏最后、也是唯一活着的线索,不能跟着标题一起降级。

再往窄走(< 560px),单条 strip 的语义会退化回现状。此时正确的做法不是继续压缩,而是 自动切多行 —— 会话一行、文件一行,以最低成本在窄屏拿到方案 A 的确定性。

做法

  • 会话降级为「头像轨道」:每条会话一个项目色字母块(复用左栏 projectAvatar 的调色板),当前会话展开成一颗带标题的药丸,其余只留色块 + hover 标题气泡。运行中的会话在色块右下角带一个脉冲小点。
  • 文件独占带标题的标签条:因为 strip 里只剩文件一种,标题 编辑区 · cc-gui 可以当作纯粹的区段名,不再承担「区分两类」的职责。
  • 会话与文件之间是 ~30px 留白 + 1px 分隔,不再是会消失的细线。
  • 当前会话始终展开,所以在编辑器里也不会丢失「回哪去」的锚点;切换会话 = 点色块,色块原地展开成药丸(有明确的形变动画可做)。
形态先例:Slack / Discord 的工作区切换器、Chrome 的标签组折叠。核心是「长期存在的身份」用紧凑色块表达,「当下在处理的内容」才配给标题宽度。

取舍

  • + 会话数增长时占用恒定,横向空间几乎全给文件标签;窗口窄时表现最好。
  • + 会话切换从「读标题」变成「认色块 + 字母」,熟练后更快;左栏与其色块同源,跨面板识别一致。
  • − 标题默认不可见:会话名首字母相近(或同一项目下多条会话)时,只靠色块 + 两字母很难区分,要 hover 才知道。这是本方案最实在的代价 —— 而窄屏会把「hover 才可见」变成「根本没空间 hover」。
  • − 未读徽章、运行状态只能收成一个小点,信息密度下降。
  • − 拖拽重排的语义变弱(色块拖拽不如标签直观),可能干脆放弃会话重排,只保留文件重排。
窄屏结论:占用最省是真的,但它把「读标题」换成了「认颜色 + 悬停」—— 悬停在一个本就没有余量的窄条上是最难成立的交互。

做法与取舍

  • strip 永远只装当前视图的标签(对话→会话标签,编辑器→文件标签),另一侧用一颗锚点 chip 表达「另一处有什么、怎么回去」。类型混淆在构造上归零。

  • 这一条就是否决理由:「agent 刚提到某文件、我要点开看」是本应用的高频动作,现状一次点击可达,方案 D 变成两次。窄屏下这个代价被放大 —— 空间越紧,你越想一步到位。
  • 但它是窄屏最省空间的形态:条内只有一种标签 + 一颗锚点,是唯一一个「不需要任何降级规则」也不会退化的方案。它的正确位置是 < 420px 的自动退化形态(手机壳 / 子会话面板),而不是主形态。
序列:宽屏用 B;中宽用 B+多行(= A 的语义);最窄(<420px)再退到 D。三者共用同一套「会话锚点态」语义,退化是连续的,不是三套设计。

窄宽度阶梯 · 中栏 760 / 560 / 400 同时对照

这一节全部由 CSS 容器查询驱动 —— 查询对象是「中栏 / 预览条自身的宽度」(容器名 tabbar,即 .center 与 .mini), 不是窗口宽度,也不是 JS 断点。理由与 styles.css 里 .chat-ledger-head 完全相同: 中栏被左右侧栏挤压时,拿窗口宽度做阈值会误判「放得下」,而拿中栏自己当容器,判断永远与实际排版一致(宽屏 3:7 分栏、手机壳、子会话面板同样成立)。

XS< 360 ⑧ 标签 max-w 120→96,⑨ 数量并入 ⋯ 菜单 色点 + 截断标题 方片,标题截断 到此为止只剩「形状 + 色点」两条线索 —— 已经等于现状的可靠性。所以 Tier S 以下不该继续压缩,该切多行。
多行模式另有两条数值:标签的 flex 地板 min-w-[170px] 在 < 460px 时降到 110px(否则一行放不下第二个标签,多行变成「一行一个」); max-h-[82px] 的三行上限在窄屏收到两行 —— 窄屏的用户更经不起条高变化。

① 容器查询,不是 JS 断点

降级规则写在 styles.css 里,用 @container tabbar (width < …) 挂到中栏的 container-type:inline-size 上。 这样侧栏开合、宽屏 3:7、手机壳、子会话面板全部自动正确,组件里一行 JS 都不用加。

复用 .chat-ledger-head 的既有模式 —— 本项目已经在这条路上,没有引入新技术。

② 形状分化必须是基底,不是增强

药丸(会话)/ 方片(文件)是唯一不占宽度的区分线索。若把它做成「宽屏才有」的样式,窄屏就会连同标题、头像一起丢掉全部线索,退化成现状。 所以 rounded-full 与 rounded-md 的分家要写在组件基底类里。

这也是「B 先行」成立的前提:它的核心收益恰好是那个不占宽度的收益。

③ 窄屏用户不让位,让「行」变多

压到 Tier S 时线索已经见底,再降只是把可用性削薄。正确的退出动作是自动切多行(会话一行 / 文件一行)—— 这正好是方案 A 的语义,以约 30px 的高度换回「不可能误点」。

于是最终形态是连续的:宽屏 B → 中宽 B+多行(=A) → 最窄(<420px)再退到 D。三档共用同一套「会话锚点态」语义,不是三套设计。

④ 会话组固定、只让文件组滚动(建议一并做)

窄屏下若两组共用一个滚动区,会话标签会被文件挤到视野外 —— 而会话是「我在哪」的答案,恰恰最不该滚出去。 建议会话组不参与横向滚动(通常 ≤3 条,~150–200px),只有文件组滚动。

这是窄屏最实在的一条改进,也是唯一一条需要动布局的(把滚动容器从「整条」改成「文件组」)。宽屏下两种做法视觉上几乎无差别,可只在窄屏启用。

⑤ 数量必须活下来

组标题逐档让位时,数量不能跟着消失 —— 它是「我还有没有没看到的标签」的唯一常驻答案。 Tier M 留 图标 + 数字,Tier XS 才把数字并进 ⋯ 菜单(那里本来就有完整列表)。

⑥ 窄屏的关闭按钮另说

现状是 hover 才出 ×。窄屏(触控)没有 hover,× 要么常驻、要么改用长按/中键。建议窄屏下激活标签的 × 常驻(已是现状),非激活标签只在选中后才出 —— 与触控语义一致。

四个方案都建议一并做的修正

① 文件组标注所属项目

文件标签存在 ideOpenFilesByProject[activeProjectId],是项目作用域;会话标签是全局的。切到别的项目的会话时右侧整组会换掉,而界面上没有任何提示。在文件组前固定标注项目名(方案 B/C 的 编辑区 · cc-gui),这类「标签去哪了」的困惑直接消失。

② 编辑器聚焦时保留会话锚点

isActive={id === activeId && !editorFocused} 让当前会话在编辑器里完全没有标记。把「视图焦点」和「会话锚点」拆成两种视觉:填充 = 正在看它,描边/侧边条 = 我是从这里来的。

③ 关闭语义的提示

会话的 × 只关标签、不中断运行中的回合;文件脏了则没有 ×。建议 hover 时给出明确说明(「关闭标签,会话继续运行」/「未保存,请先保存」),让「× 点了会怎样」可预期。

④ 溢出菜单也按组分节

TabBarOverflowMenu 现在把两类标签平铺成一条列表,同样混淆。加两个小节标题(会话 / 编辑区 · 项目),与条上的分组口径保持一致。窄屏下标题降级后,这个菜单还是唯一的完整信息出口 —— 更要做对。

⑤ 多行模式下的分组也要成立

多行换行时两类标签会混在同一片网格里,分组线彻底失效。方案 B 的窄屏逃生舱要求换行后仍是「会话一行 / 文件一行」两片,而不是交错 —— 即 多行的断行点由分组决定,而不是由宽度自然折行。

⑥ 新建会话入口

tab 模式目前没有新建会话的按钮(要去左栏)。在会话组尾部补一个 +,与「会话组」这个语义块绑定,顺带强化分组的存在感。

⑦ 窄宽度用容器查询自动化(本次新增)

不要新增「窄屏开关」这类设置项。把降级规则写成 @container tabbar (width < N)(容器 = 中栏),全部交给 CSS。 唯一需要 JS 的是两个结构级切换:<560px 自动进多行、<420px 退上下文条 —— 用 ResizeObserver 读中栏宽度写进 store(与 tabBarMultiRow 同一套状态),而不是新增配置。

极窄(<560 自动多行,<420 退 D):压到 Tier S 时线索已经见底(只剩形状 + 色点),继续压缩只是把可用性削薄。此时自动切多行 = 用 30px 换回 A 的「不可能误点」;再窄就退到 D 的上下文条 —— 条内只有一种标签,是唯一不需要降级规则也不会退化的形态。
A 的实现量最大,但它在窄屏上的收益是零降级成本,所以是「窄屏的正确答案」;把它作为 B 的窄屏退化路径,正好用 B 的样式系统去承载 A 的结构,不必重做视觉。
C 只在会话数量长期很多、且习惯用颜色/字母而不是标题找人时更优,且窄屏会把「悬停才可见」的代价放大。
